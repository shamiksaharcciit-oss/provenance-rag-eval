## 1. Substantive: the stored `p_raw` values are Monte-Carlo, not exact enumeration

§6 of the sealed text declares the method as:

> "Exact sign-flip enumeration over the 2\*\*K assignments of the K discordant pairs (== McNemar
> exact). K reported for every cell. `p_mc_10k` retained beside it."

The eight `p_raw` values carried into the freeze do not come from that procedure. They come from
`paired_permutation_p` in `src/stats/tests.py`, which is a Monte-Carlo sign-flip with
`(count + 1) / (iters + 1)` smoothing.

Three lines of evidence, and I want to be explicit that the first one is the one that decides it:

1. **No stored value equals any exact tail.** I brute-forced every feasible (b, c) discordant
   split per cell under the constraint `b − c = round(delta × n)`, with K running to n, and
   computed the exact two-sided binomial tail under all three conventions in use — inclusive,
   exclusive, and mid-p. Not one cell's stored `p_raw` matches any of them. If §6's procedure had
   produced these numbers, at least one would have to.
2. `exact_signflip_p` exists in `src/stats/tests.py` and does the enumeration correctly (it even
   raises `NotEqualMagnitudeDiffs` on non-binary input). But its file's mtime postdates the
   2026-07-24 published runs. It was written after the numbers it is credited with.
3. The 5-decimal granularity of the stored values is consistent with the smoothing denominator,
   not with a rational exact tail.

I over-inferred once here and want to flag it so you can discount it: before I read
`src/stats/tests.py` I briefly concluded from the granularity alone that these were
100,000-replicate values. Granularity alone does not establish that. The mechanism in the source
does, and the brute-force does.

**Nothing moves.** I enumerated the entire feasible exact-p range per cell — every (b, c) split
compatible with the observed delta, within ±0.01 of each stored value — and ran Holm over all
combinations. **All three families yield exactly one distinct classification vector across the
whole feasible set, identical to the frozen one.** The 2.4 disagreement survives too: the nearest
feasible exact p for the secondary bge/Track B cell is 0.065430, still above 0.05, while the CI
still excludes zero. So the three-criteria disagreement you found is a property of the data, not
an artifact of the p-value procedure.

**Disposition — and this is the part that matters.** The stamped inputs do not change. The
one-shot rule means a stamped value is stamped whether or not I later prefer a different
estimator for it. What should happen instead:

- Record an erratum against §6: the declared method describes `exact_signflip_p`; the carried
  values were produced by `paired_permutation_p`. State the discrepancy plainly rather than
  reconciling it.
- Compute the exact table with `exact_signflip_p` and record it **beside** the stamped values,
  labelled as a post-stamp recomputation, with K reported per cell as §6 already requires.
- Record the invariance proof above alongside it, so a reader can see the erratum is bounded.

That sequence keeps the integrity property intact: the freeze records what was frozen, and the
correction is additive and dated. Editing the stamped p's to "fix" them would destroy exactly the
property the freeze exists to establish, even though the numbers would end up more accurate.

This is a fifth data point for PROC-1, and it is a different failure mode from the other four:
not an incomplete criteria rule, but a **declared** procedure that does not match the executed
one. Worth naming as its own class in PROC-1 — declaration/implementation divergence — because
the authoring gate that catches an incomplete rule will not catch this one.

## 2. The CI procedure is never named in the freeze

§5 asserts that three criteria agree on all six primary cells. Two of the three are specified —
the Holm-corrected test, and `branch_1_significance` governing which one binds. The third,
"the CI excludes zero," names a criterion but never names the procedure that produces the CI.

This would be pedantic if the three always agreed. They do not: your 2.4 finding is precisely the
cell where the CI says one thing and the test says another. And because they disagree, **the CI
cannot be the test's inversion.** It is a second, independent inferential procedure — the paired
bootstrap percentile interval from `paired_bootstrap_diff`, whose `significant_ci` field name
traces straight through into `results_pw1/guard1_family1_minilm_A.json`.

So the sealed text asserts agreement among three criteria while specifying two of them, and the
unspecified one is the one that binds on the eighth cell. By the §A5 standard — one quantity, one
procedure, exhaustive and disjoint — that is a gap, and it is sitting inside the document that
records PROC-1.

**Disposition:** erratum naming the procedure explicitly — `paired_bootstrap_diff`, percentile
method, iteration count and seed — as the CI's definition, with a note that it is a second
procedure and not an inversion of the test. This is a documentation completion, not a change to
any number, so it does not disturb the stamp.

## 3. The A7 halt does not cover the NOT APPLICABLE branch

`interpret.py:69`, inside `classify_cell`:

```python
if not full_significant:
    r = None if delta_full == 0.0 else delta_corrected / delta_full   # no halt
    return {"branch": "NOT APPLICABLE", "r": r, ...}
```

The division happens before `retention_ratio` is ever reached, so the `RatioExceedsOne` guard
never runs on this path. `test_branch_1_not_applicable_short_circuits_and_still_reports_r`
deliberately pins this behaviour — it asserts `out["r"] == pytest.approx(0.0100 / 0.0267)` with
no halt — so this is intended code, not an oversight in the diff sense.

But the frozen `halt_conditions` says:

> `"r > 1.0 for any cell -> scoring defect"`

**Any cell.** And with the secondary family now specified, **four of the eight frozen cells are
NOT APPLICABLE** — MiniLM/B in family 1, bge/A in family 2, and both secondary cells. Half the
grid takes the unguarded path. The module docstring's own argument applies with full force there:
stripping ranges is monotone in hits, the unformatted arm has nothing to strip, so `r > 1` is a
scoring defect regardless of whether the cell's `delta_full` cleared significance. A defect does
not become descriptive because the cell it appears in is descriptive.

**Framing, and I think this one is unambiguous:** the code under-implements a stamped rule. The
freeze is correct and the code is narrower than it. So the fix is to the code and to the test —
hoist the `r > 1.0` check so it runs on every path that computes `r` — and the freeze is
untouched. That is a pre-arm code change, and it is small.

While you are in there: `retention_ratio` raises `ZeroDivisionError` on `delta_full == 0.0`, but
the NOT APPLICABLE path returns `r = None` for the same input. Both are defensible; they should
be the same decision, made once.

A7 is answered, and better than I asked. `test_r_exactly_one_is_allowed` and
`test_float_slack_does_not_become_a_tolerance_for_real_overshoot` together pin the boundary from
both sides, so the fact that the step-5 sweep never actually reaches `r = 1.0` does not leave the
boundary untested. I withdraw the concern.

## 6. Pin the guard-1 environment before B4

`results_pw1/guard1_minilm_A.json` records no environment: no library versions, no Python
version, no hardware note. For the family-2 cell that is fine — it is a re-score of persisted
artifacts from `run-20260724-135411`, and a re-score's evidential value comes from the artifacts.

But **family 1 was verified by a full re-run**, because — as the file itself records — no
persisted per-query vectors exist for the size-matched control. That re-run reproduced 0.5682 and
0.7216 to four decimals, which is a strong result. Its evidential value depends entirely on the
environment being the same one that produced the published numbers, and nothing in the artifact
establishes that. Right now the record says "it reproduced" without saying "under what."

At minimum: `sentence-transformers`, `torch`, `faiss` (1.14.3 is already the paper's figure),
`numpy`, `rank_bm25`, Python version, and whether CPU or GPU. Embedding models are not
bit-identical across `torch` versions or across CPU/GPU, and a recall metric on 176 queries can
absorb a small numerical difference without moving — which is the case where you most want the
record, because you cannot tell from the result that it happened.

This is cheap, it is still pre-arm, and it makes B4's remaining guard-1 cells worth more. It also
applies forward to every arm, since the arms are re-scorings whose comparability to the published
numbers is the whole point.

**And the guard-4 lesson, which I want to state as a rule because it will recur:** a guard whose
correct behaviour is exact equality must assert equality and halt, never report a rate. Your first
checker reported 138/147 and 148/160 — 92–94%, which reads as "mostly fine" and would very
plausibly have been accepted as a rebuild tolerance. The true value was 147/147 and 160/160. A
rate absorbs a bug; an exact count cannot. Same tier as NC-A/NC-B, and worth adding to the
criteria template beside §A1b.
